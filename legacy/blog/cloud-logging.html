Cloud logging: как да събирате и използвате логовете?

Cloud logging е проектиран процес за събиране, маршрутизиране, защита, търсене и преглед на събития от cloud control plane, ресурси и workloads. Наличието на provider activity history не гарантира пълно coverage, достатъчна retention, централно копие или alerts; всяка от тези цели изисква отделно решение и проверка.

Изображението е mock alerts dashboard за визуален контекст, не provider portal или реално log хранилище.

Кратък модел: определете какво трябва да знаете, включете правилните event sources, маршрутизирайте към защитени destinations, задайте retention и права, направете detection/use cases и алармирайте при спиране на самия logging pipeline. Събирайте повече data само когато това оправдава privacy, операционния и финансовия разход.

Какво наричаме cloud log?

Тази статия се фокусира върху събития, полезни за security, audit и incident investigation; metrics и traces са различни сигнали за monitoring и performance.

Тип събитиеКакво показваПример
Control plane / managementПромени по ресурси, identities, policies и provider configuration.Създаден cloud account/resource, role assignment променен или logging setting изключен.
Data plane / resource accessОперации върху данни или действия вътре в конкретна услуга.S3 object read, Key Vault secret access, database query или GCP Data Access event.
Workload / applicationСъбития от OS, runtime, containers, application code и dependencies.Application authentication failure, OS security event или container runtime activity.
Network / security toolingНаблюдения от firewall, flow logs, WAF, identity/security tools и detections.Неочаквана комуникация, denied request или security finding, според услугата и конфигурацията.

Provider audit logs покриват конкретни control/data-plane операции; те не са заместител на всички application, host, container, database и network logs. Направете source inventory за всеки critical workload и отбележете кои източници изискват отделна инсталация, diagnostic setting или платен data event capture.

Какво се включва по подразбиране?

Trails/event data stores не записват data events по подразбиране; избират се ресурсите/event types и се проверява цената.

От източника до investigation

  1. Определете use case. Например да се вижда промяна в production IAM, четене на чувствителен object или спиране на audit pipeline.
  2. Изберете източниците и categories. Mapping-ът трябва да покрива accounts/subscriptions/projects, Regions, resources, management и data-plane events и workload logs.
  3. Маршрутизирайте данните. Използвайте provider destinations или централизиран log/SIEM pipeline според анализ, retention, privacy, location и availability изискванията.
  4. Защитете logs и routing. Ограничете кой може да чете, изтрива или променя logs, sinks, trails и diagnostic settings; отделете administration на хранилището от workload owners, където моделът го позволява.
  5. Направете searches и detections. Съпоставете actor, timestamp, resource, action, result и related events; настройте alert criteria с owner и escalation path.
  6. Проверявайте pipeline-а. Алармирайте при прекъсната ingestion, спрян trail, премахнат diagnostic setting, неочаквано паднал event volume или грешка в routing destination.
  7. Упражнете разследването. Проверете дали логовете се намират, корелират между accounts/services, запазват нужните details и стигат до responders.

Централизация, integrity и достъп

Централното хранилище може да помогне за корелация между accounts и да отдели audit records от ежедневното управление на workloads. Определете отделни permissions за routing, log administration и read-only investigation; ограничете промяната на log retention и delete/stop operations до малък брой identities и логвайте и тези действия.

При нужда от доказателства или дълга retention изберете подходящи integrity, versioning, immutable/locked storage или provider validation capabilities и проверете operational consequences. Не приемайте, че всяка централизирана destination е автоматично immutable или че всички provider logs имат еднакви guarantees.

Планирайте часови източници и timestamp interpretation, Region/resource identifiers, field normalization и account/tenant mapping. Липсващ actor context, различни schemas или ingestion delay може да затруднят timeline; документирайте gaps вместо да третирате отсъствието на запис като доказателство, че действие не е имало.

Retention, privacy и cost

  • Retention: задайте срок по audit, investigation, contract и applicable requirements; разделете interactive query period от archive period, ако е нужно.
  • Cost: включете ingestion, storage, queries, exports и cross-region/third-party transfer; AWS data events и Google Data Access logs могат да добавят обем и такси.
  • Coverage: не изключвайте важни categories само заради обем без да разберете какво губите за audit/response.
  • Privacy: логовете може да съдържат identities, IPs, resource names и application payloads; minimization, access, location и retention изискват policy и owner.
  • Secrets: не логвайте access tokens, passwords, signing keys или чувствителни payloads; ревизирайте custom application logs и debug modes.
  • Alerts: настройвайте прагове и дедупликация спрямо use case; шумните или необработвани alerts не са полезно monitoring.

Практичен deployment checklist

  1. Опишете critical accounts/projects/subscriptions, services, data owners и incident scenarios.
  2. Направете log-source matrix с control-plane, data-plane, workload и network/security sources.
  3. Отбележете default coverage, categories, Regions/scopes и gaps, които изискват явна конфигурация.
  4. Изберете retention, destinations, access model, integrity protection, data location и estimated cost.
  5. Определете detection owner, alert routing, response contacts и pipeline health checks.
  6. Изпълнете safe test event за всяка critical source и потвърдете ingestion, query, alert и escalation.
  7. Преглеждайте source coverage, permissions и spend при добавяне на service/account и поне според вътрешния review cycle.

Често задавани въпроси

Cloud logging покрива ли всички дейности в cloud средата?

Не автоматично. Default coverage се различава по provider и service. Някои data-plane или resource logs изискват изрична конфигурация, а application, OS и network logs може да са отделни източници.

Колко дълго се пазят cloud logs по подразбиране?

Няма един общ срок. Например AWS CloudTrail Event history и Azure Activity Log имат 90-дневен обхват, докато Google Cloud Logging използва различни срокове за _Required и _Default bucket. Проверете актуалния provider scope, retention настройки и отделните архиви.

Логовете генерират ли се автоматично?

Само част от тях. AWS Event history и Azure Activity Log включват определени management events; AWS data events, Azure resource logs и повечето Google Cloud Data Access audit logs изискват service-specific конфигурация, с provider/service exceptions.

Достатъчно ли е логовете да се съхраняват?

Не. Определете кой ги преглежда, как се създават alerts, кой може да променя routing/retention, как се открива прекъсване на ingestion и какви са escalation действията.

Как да контролирам разходите за cloud logging?

Започнете от нужните event categories и retention/use cases. Изберете подходящите sources и destinations, измервайте ingestion и storage, включете разхода от data events и analytics и филтрирайте само след оценка на audit/response последствията.
